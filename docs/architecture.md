# Architecture — Alpha

## Overview

Frontend (React) talks to two backend entry points: a REST API for users, workspaces and reads, and a SignalR hub for everything that changes shared canvas state. Both call one shared service layer, which is the only thing that touches the database.

The rule: anything other people on a workspace need to see live — assets, their items, their layout — changes only through the hub. REST covers what happens before a workspace is joined (identity, creating workspaces, adding members) and plain reads.

Containment: a **User** belongs to one or more **Workspace**s. A **Workspace** contains **Asset**s — a wrapper around a typed content object (`TemplateType`, `Todo` only for alpha). Workspace membership gates what's listed for a user; it isn't role-based — RBAC (owner/editor/viewer per asset) stays out of scope, see `alpha.md`.

CORS is enabled from the start, for both the REST API and the hub, with allowed origins read from configuration so production can set its own. Credentials are allowed, so origins are listed explicitly, never a wildcard.

Exact request/response/payload shapes are in `api-contract.md` — this doc covers design, that one covers the wire format backend and frontend both build against.

## Entities

- **User** — a person using the app.
- **Workspace** — a shared space; contains assets, has members.
- **Asset** — a card on a workspace; wraps typed content (`Todo` only in alpha).
- **TodoItem** — one entry inside a Todo asset.

### User

| Field | Type | Holds |
|---|---|---|
| `Id` | uuid | Identity, generated by the server. |
| `DisplayName` | string | Name shown to others; no auth, so not unique. |
| `CreatedAt` | datetime, UTC | When the user was created. |

### Workspace

| Field | Type | Holds |
|---|---|---|
| `Id` | uuid | Identity. |
| `Name` | string | Workspace name. |
| `CreatedAt` | datetime, UTC | When it was created. |
| `Users` | many-to-many navigation | Members. Membership gates what is listed for a user. |
| `Assets` | one-to-many navigation | The assets on this workspace. |

### Asset

| Field | Type | Holds |
|---|---|---|
| `Id` | uuid | Identity. |
| `Title` | string | Card title. |
| `TemplateType` | enum | The kind of asset; only `Todo` in alpha. Decides how the card renders. |
| `WorkspaceId` | uuid, ForeignKey→Workspace | The workspace it lives on. |
| `Items` | one-to-many navigation | Its `TodoItem`s. |
| `X`, `Y` | float | Canvas position. Stored now, unused in alpha. |
| `SizeX`, `SizeY` | float | Canvas size. Stored now, unused in alpha. |
| `ZPos` | int | Stacking order on the canvas. Stored now, unused in alpha. |
| `CreatedAt`, `UpdatedAt` | datetime, UTC | Creation time; last content change. |

There is no revision field. Concurrent changes are merged by delta, see Concurrency. The `Revision` column and `[ConcurrencyCheck]` that exist today are removed by a migration in the backend work.

### TodoItem

| Field | Type | Holds |
|---|---|---|
| `Id` | uuid | Identity. For a new item the client generates it, so the same delta can be applied twice safely. |
| `AssetId` | uuid, ForeignKey→Asset | The asset it belongs to. |
| `Text` | string | The entry's text; non-empty, at most 200 characters. |
| `IsDone` | bool | Whether it is ticked. |
| `Order` | int | Position in the list, ascending. Duplicates are allowed and tie-break by `Id`. |

## REST API

### UsersController — `/api/users`

| Endpoint | Description |
|---|---|
| `POST /api/users` | Creates a user from a display name, returns the user id. |
| `GET /api/users/{id}` | Returns a user's display name. |

### WorkspacesController — `/api/workspaces`

| Endpoint | Description |
|---|---|
| `POST /api/workspaces` | Creates a workspace and adds the creator as its first member. |
| `GET /api/workspaces?userId=` | Lists workspaces the given user is a member of. `userId` is required. |
| `POST /api/workspaces/{id}/members` | Adds a user to the workspace. No permission check — any caller naming a `userId` can add it, consistent with alpha having no real auth. |
| `DELETE /api/workspaces/{id}` | Deletes a workspace. |

### AssetsController — `/api/assets`

| Endpoint | Description |
|---|---|
| `GET /api/assets/presets` | Lists the server-defined presets (name + item count) that `CreateAsset` can seed a new asset from. |

Assets are created (optionally seeded from a preset), read and deleted through the hub, not here. The remaining REST asset endpoints (`POST /api/assets`, `GET /api/assets`, `GET /api/assets/{id}`, `DELETE /api/assets/{id}`) are removed once the hub is in.

Validation failures return the framework-default 400 `application/problem+json` body. A missing workspace/user returns an empty 404.

Membership is not a security boundary for REST — there's no auth to make that meaningful yet. It governs what's *listed* for a user. The hub does check it: `JoinWorkspace` asks `WorkspaceService.IsMemberAsync` and rejects non-members. The `userId` is still sent by the client, so this stops mistakes, not impersonation.

## SignalR Hub — `WorkspaceHub` at `/hubs/workspace`

One group per workspace. A connection joins a workspace and receives every change to every asset on it, so the hub is named for the group it serves. The assets' content is changed by sending a *delta* (only what changed), so there is one update method per entity, not one per kind of edit. Every method other than `JoinWorkspace` requires the calling connection to have joined the workspace first.

### Client → Server

| Method | Description |
|---|---|
| `JoinWorkspace(workspaceId, userId)` | Adds the connection to the workspace's group, registers presence, notifies the group, and returns the workspace's current state: every asset with its items, plus who is already viewing. The group is joined *before* the state is read, so no change can slip between the read and the first broadcast. |
| `LeaveWorkspace(workspaceId)` | Removes the connection from the group and presence. |
| `CreateAsset(workspaceId, title, templateType?, presetName?)` | Creates an asset. `templateType` defaults to `Todo`. If `presetName` names a server-defined preset, the asset is created with that template's items; otherwise it is empty. The client sends only the name, never item content, and an unknown name throws a `HubException`. Seeding happens only here — templates can't be applied to an existing asset. |
| `UpdateAsset(assetId, delta)` | Applies a delta to the asset's content, see below. |
| `DeleteAsset(assetId)` | Deletes an asset. |

### The delta

A delta holds only what changed. Every part is optional.

| Part | Holds |
|---|---|
| `title` | The new title. |
| `added` | New items: `id` (client-generated uuid), `text`, `isDone`, `order`. |
| `updated` | Changed items: `id` plus any of `text`, `isDone`, `order`. A field left out is unchanged; a field present is set. |
| `deleted` | Ids of items to remove. |

The server applies a whole delta in one transaction or not at all. Entries that refer to an item that isn't in the asset (never existed, or deleted by someone else a moment ago) are skipped, not errors. A new item whose `id` already exists, empty or over-long `text`, or an unknown asset throws a `HubException`.

Reordering is not a separate operation: the client sends the new `order` only for the items it moved. No other item is touched, so two people reordering at once can't corrupt each other's lists; equal `order` values tie-break by `Id`.

Clients send a delta on commit (enter, blur, toggle, end of a drag), not per keystroke.

### Server → Client

Every asset event carries `assetId`, since one connection receives events for all assets on the workspace.

| Event | Description |
|---|---|
| `AssetCreated(asset)` | Broadcast to the whole group, including the sender, when `CreateAsset` succeeds. `asset` includes any seeded items. |
| `AssetUpdated(assetId, delta)` | Broadcast to the whole group, including the sender, when `UpdateAsset` is applied. The delta is what was actually applied — skipped entries are removed — so applying it keeps every client in step. |
| `AssetDeleted(assetId)` | Broadcast when `DeleteAsset` succeeds. |
| `UserJoined(userId, displayName)` | Broadcast when a user joins the workspace. |
| `UserLeft(userId)` | Broadcast when a user leaves the workspace. |

A hub method that targets a missing workspace/asset, or fails validation, throws a `HubException` — SignalR surfaces this as a rejected invocation to the caller only. The caller discards its optimistic change and resyncs by calling `JoinWorkspace` again.

On disconnect — explicit `LeaveWorkspace`, or an ungraceful drop (tab closed, network loss) handled by overriding `OnDisconnectedAsync` — the hub looks up the workspaces this connection was present in via `PresenceService`, removes it, and broadcasts `UserLeft` for each. Presence is keyed by connection id specifically so this lookup works without the client having to say anything on its way out.

### Layout (beta)

Not built in alpha; the columns exist (see Entities). Layout operations — `MoveAsset(assetId, x, y)`, with resize and z-order the same way — are last-write-wins:

- The client moves the card locally and calls the hub only on drop, never during the drag.
- The server validates (asset exists, caller is in the workspace, values are sane) and saves.
- On success the server broadcasts `AssetMoved(assetId, x, y)` to the whole group, including the sender. On failure it sends `AssetMoved` with the asset's current coordinates to the caller only. Either way the client shows the coordinates it receives.
- Someone can drag a card another user is working on. That is accepted.

## Service Layer

| Service | Responsibility |
|---|---|
| `WorkspaceService` | Creates a workspace (adding the creator as its first member), adds members, lists a user's workspaces. |
| `AssetService` | Creates an asset (choosing initial content by `TemplateType`, seeding items from `PresetCatalog` when a `presetName` is given), loads a workspace's assets for `JoinWorkspace`, applies a delta (`ApplyDeltaAsync`), deletes an asset. |
| `PresenceService` | Tracks which connections are viewing which workspace, in memory, keyed by connection id. |
| `UserService` | Creates and reads users. |

`UpdateAsset` calls `ApplyDeltaAsync`, which validates the delta, applies it in one transaction and returns the delta that was actually applied for the hub to broadcast.

## Validation

Data Annotations on REST DTOs (`[Required]`, `[MaxLength]`) for shape validation — display name, workspace/asset name/title, item text non-empty and within length limits. The framework rejects malformed requests with a 400 before a handler runs. Rules that need DB access (e.g. an `itemId` belongs to the given `assetId`) aren't shape validation and live in the relevant service, not on a DTO. SignalR doesn't run Data Annotations on hub arguments, so hub payloads are validated explicitly in `AssetService`: every part of a delta, including that item `text` is non-empty and within the length limit.

## Data Access

**SQLite** — single file, no external DB process to run in dev. Chosen for alpha because the goal is proving real-time sync and merging work, not production-grade storage; revisit for beta if real concurrent-load behavior needs testing.

**Assets are persisted in SQLite through EF Core**, alongside users and workspaces. `AssetService` depends on an `IAssetStore` abstraction rather than a concrete store (Dependency Inversion): `EfAssetStore` reads and writes the `Asset` and `TodoItem` tables so assets survive a restart, while `InMemoryAssetStore` implements the same interface as an alternate, non-persistent store. Only `AssetService` uses the store.

`Workspace`-`User` membership uses EF Core's skip navigations (`Workspace.Users`, `User.Workspaces`, both `ICollection<T>`) rather than an explicit join entity — EF generates and manages the bridge table itself. No membership class to write or maintain; add one back only if membership ever needs its own data (a role, a joined-at timestamp exposed to the API, etc.) beyond the plain yes/no it is now.

Services talk to the database through EF Core's `DbContext`/`DbSet<T>` directly — no repository layer. `DbContext` already provides Unit of Work (batches changes, commits them as one transaction on `SaveChangesAsync`) and per-entity querying, so a hand-rolled repository on top would just forward to it. Entities are plain C# classes; EF maps them to tables and translates LINQ queries into SQL.

## Concurrency

There is no revision. Edits are deltas, and a delta only names what it changes, so concurrent changes merge instead of conflicting:

| Concurrent changes | Result |
|---|---|
| Two additions | Both items exist. |
| Edits to different items | Both apply. |
| Edits to different fields of one item | Both apply (EF writes only the columns that changed). |
| Edits to the same field of one item | The later write wins. |
| Edit and delete of the same item | The item is gone; the edit is skipped. |
| Two reorders | Each moves only the items it names; equal `order` values tie-break by `Id`. |

A delta is applied in a single `SaveChangesAsync()`, so it is all-or-nothing. If an item is deleted between loading and saving, EF reports zero rows affected and throws `DbUpdateConcurrencyException`; `AssetService` reloads and reapplies the delta once, now skipping the deleted item. Because every item has its own id, applying the same delta twice is harmless on the client (an `added` item whose id it already has is ignored), which is what lets the sender safely apply its own change optimistically and again when the broadcast returns.

For one asset, applying a delta and broadcasting it happen under a per-asset lock, so the order clients receive deltas is the order they were saved. Without it, two concurrent deltas could save as A then B but broadcast as B then A, leaving clients showing A's value while the database holds B's. A single backend instance is assumed for alpha.

Layout edits (beta) are last-write-wins, saved with a direct `UPDATE` (`ExecuteUpdateAsync`) that doesn't load the entity. See Layout (beta) in the hub section.

The cost: two people editing the same field of the same item silently lose one edit. That is accepted for alpha.

## Routing

React Router, two routes. There is no per-asset route: a workspace is a canvas, and its assets live on it and are edited inline.

| Route | Renders |
|---|---|
| `/` | Workspaces the current user belongs to — list/create. |
| `/workspaces/:workspaceId` | The workspace canvas — its assets, edited inline, with live sync. The id comes from the URL, so refresh and shareable links work. |

## Frontend State

Context + `useReducer`, scoped to the workspace canvas (the one screen with real-time state). Each hub event maps to a reducer action (`ASSET_CREATED`, `ASSET_UPDATED`, `ASSET_DELETED`, `USER_JOINED`, `USER_LEFT`), plus a `LOCAL_EDIT` action that applies a delta optimistically. `ASSET_UPDATED` and `LOCAL_EDIT` share one delta-applying function. A `WorkspaceProvider` (singular) owns the reducer, seeded from the `JoinWorkspace` response; child components read state and dispatch via context instead of prop drilling. The workspaces list is plain REST data, no reducer needed — it's not edited in real time. A separate `WorkspaceListProvider` (plural, read with `useWorkspaceList()`) loads it once per user and shares it between the overview and the sidebar, reloading after a workspace is created.

## Frontend Flow

1. On boot, load `{userId, displayName}` from localStorage, or create one via `POST /api/users`.
2. `/` lists the user's workspaces (`GET /api/workspaces?userId=`); creating one calls `POST /api/workspaces` and navigates into it.
3. `/workspaces/:workspaceId` is the canvas. Opening it connects to the hub and calls `JoinWorkspace`, whose response replaces state entirely. This runs on every connect, including reconnects after a dropped connection, so the client never resumes from state that might have missed edits made while it was offline. Events that arrive while the join is in flight are buffered and applied after the response, since the response may be older than they are.
4. Creating an asset (optionally from a preset) and deleting one happen on the canvas through the hub (`CreateAsset`, `DeleteAsset`). The preset list for the picker comes from `GET /api/assets/presets`; the chosen name goes in `CreateAsset`.
5. Editing builds a delta, applies it locally right away (`LOCAL_EDIT`), then sends it with `UpdateAsset`. It is sent on commit (enter, blur, toggle, end of a drag), not per keystroke. The broadcast `AssetUpdated` is applied too; it is idempotent, so the sender's own echo changes nothing.
6. If `UpdateAsset` is rejected with a `HubException`, the client discards its optimistic change and calls `JoinWorkspace` again to resync.
7. Leaving the canvas leaves the workspace on the hub and closes the connection.

## Deferred

Not part of alpha, decided later:

- **CI** — no GitHub Actions gate on PRs yet.
- **Deployment/hosting** — no target environment chosen yet.
- **RBAC** — per-asset owner/editor/viewer roles. Workspace membership (this doc) is a flat yes/no gate, not a replacement for this.
- **Canvas layout operations** — moving and resizing assets over the hub. The rule is decided (last-write-wins, see Layout (beta)), the operations themselves are beta. `tbd.md` records the decision.
